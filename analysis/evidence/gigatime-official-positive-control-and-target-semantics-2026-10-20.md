# Official GigaTIME positive control and output semantics

The [official GigaTIME repository](https://github.com/prov-gigatime/GigaTIME#data) supplies 50 paired H&E/COMET test patches. Its 418,489,537-byte `sample_test_data.zip` was downloaded locally and passed ZIP CRC validation (SHA-256 `cd1212b361f7bfe4f7f01779a59f437c691fd43a684d7b5f584c37bf7d0e2601`). The archive contains 50 RGB H&E PNGs, 50 25-channel raw COMET NumPy arrays, and associated mask/metadata files. One fixed pair, `0_556_556_556`, was staged on Chiamaka as a **CPU-only positive control** at `/home/chiamaka/Tambua-gigatime-official-positive-control-2026-10-20/input`. The lossless RGB OME-TIFF and raw COMET channel-0 OME-TIFF are 556 × 556 pixels with a declared source spacing of 128/556 = 0.2302158 µm/pixel. Transfer hashes were checked on both machines. The pinned GigaTIME CNN completed one CPU inference at exactly 0.25 µm/pixel with a single 512 × 512 output tile and passing distribution/seam technical checks. The [side-by-side image](gigatime-official-positive-control-2026-10-20/official-positive-control-contact.webp) shows coarse but visually nuclear virtual DAPI on the paired control. The raw COMET channel-0 mapping is still treated as a candidate nuclear channel; the 25-channel COMET array and 23-channel model output differ, and the [official issue](https://github.com/prov-gigatime/GigaTIME/issues/14) does not resolve that array's exact map. It is not used for a numerical measured-DAPI score.

The [authors' training script](https://github.com/prov-gigatime/GigaTIME/blob/main/scripts/db_train.py) explicitly downsamples each 512-pixel marker target eightfold with bilinear interpolation, then upsamples it back to 512 pixels before computing loss. At the [authors' clarified physical field size](https://github.com/prov-gigatime/GigaTIME/issues/4) of 128 µm per 512 model pixels, the supervised target's intermediate grid has 64 samples across 128 µm, or **2 µm per coarse sample**. The [dataset code](https://github.com/prov-gigatime/GigaTIME/blob/main/scripts/prov_data.py) constructs cell-level, binarized marker masks for those targets. GigaTIME output therefore must be treated as an **uncalibrated virtual marker score**, not measured fluorescence intensity or guaranteed single-nucleus contours. CellPhenotyper already records this value semantics in its output metadata.

This training design can contribute to broad virtual-DAPI peaks, but it does **not** by itself explain the MoNuSAC QC failures. In the prior [ideal coarse-target audit](monusac-expanded-output-qc/first-twenty-one-ideal-coarse-qc.json), a perfect eightfold-coarsened StarDist mask passed the unchanged nuclear gate in all first 21 fields, while the actual virtual DAPI failed all 21. That optimistic self-mask control does not measure real model accuracy. The official paired positive control supports the pinned inference code, RGB handling and calibrated scale on a source-domain patch; the stark difference from many MoNuSAC fields calls for a domain-transfer and input-normalization investigation. It does not validate protein-specific correlation on ORION or four-class cell typing on MoNuSAC.

No UCT HPC GPU work was used. The independent 93-field Chiamaka CPU bundle finished with nine automatic DAPI-QC passes and 84 failures. A separately authorized, one-field Chiamaka GPU pilot on registered ORION CRC04 generated all 23 spatial channels and verified owned-process and GPU-context cleanup. Its raw protein comparison shows poor marker-specific agreement despite passing DAPI and seam checks; see [the CRC04 visual review](orion-raw-marker-visual-review-CRC04-2026-10-20/visual-review.json). These observations support the inference implementation and expose a model-transfer/marker-specificity limitation; they do not justify relaxing the MoNuSAC nuclear gate or claiming that a cell-type model has been validated.
